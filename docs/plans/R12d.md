# R12d — live child grant views

The built-in subagent receives a per-subject view of live grants, not the parent's unrestricted
registry. Own records match normally; ancestor records match only when `delegable: true`.
Both allow and deny records filter this way. Ordinary first-match ordering and R13c's fresh
boundary selection of any applicable deny remain unchanged. Explicit shared base-policy rules
(including blanket allow/yolo) are separate authority and deliberately unchanged; grant filtering
does not claim to narrow an explicit base rule.

## Lifecycle and bounds

`PermissionGrantRegistry.childView()` creates a fresh subject sharing one bounded backing store,
audit queue and counters. No grant IDs, approvals or counts are cloned. Views inherit live
additions/revocations in their ancestor chain, not sibling records. Root authorization never
consumes child-owned records. Root inspection sees child subjects/scopes and can revoke any exact
ID; a child can revoke only its own records. Matched-decision counts belong to the original grant
and accumulate once for actual matched decisions, never previews or bypassed fresh-boundary allows.

Each view is sealed to its creation root session and task UUID. At root task end, child-owned
records (including session-duration standing answers) are revoked and all existing views expire.
An old child cannot acquire authority from the next turn, even in the same resumed conversation.
Paused/resumed execution within the same live task retains its view. Events, origin strings,
resume IDs and generated briefs cannot reactivate a view. Audit append failure retains queued
changes and prevents grant dispatch, as before; expiry still invalidates views if cleanup fails.

Backing limits remain 256 grants / 1,024 pending changes by default, with validated maximum 4,096.
`maxViews` defaults to 256 cumulative child subjects per root run (validated 1–4,096), and ancestry
is capped at 64 hops. Limits are shared by all views, fail explicitly and never silently evict
authority or audit changes. The owner index and view count reset at root task end; old externally
retained view objects stay inactive. A child cannot invoke root lifecycle methods or reset a
backing audit-blocked state. Records are still lexical/advisory scopes, not OS containment.

## Actual runtime and approval path

The runtime binds the current registry and session/task snapshot to the exact `ToolContext`
object immediately before tool execution. The built-in subagent derives its view from that
internal live binding, overriding accidental root registry reuse in `childConfig`; descendants
derive from their current parent view. Copied/unbound contexts cannot recover configured root
grants, and stale bindings cannot cross a later task. This is a trusted host-code boundary, not
a JavaScript sandbox against malicious SDK integrations.

`onAsk(req, context?)` adds optional same-call context containing the actual view. Existing
one-argument handlers remain callable. The built-in TUI uses the supplied view for its standing
peek, scope preview and installation. An explicitly supplied context without a registry cannot
fall back to root grants; it supports one-time answers only. A fresh explicit child answer can
authorize the current request independently, and standing/scoped answers create child-owned
records. Both input paths preview that subject and describe the effective child/current-parent-run
lifetime. Root inspection displays those records and their exact subject/IDs.

Arbitrary trusted one-argument handlers can still explicitly approve, ignore context or access
the root registry themselves; this API does not sandbox custom callbacks. The built-in forwarding
path retains the context. Sandbox escalation, MCP-definition-change consent and external-input
expansion remain separate one-time consent and cannot create standing/scoped grants. Model prose,
MCP hints and tool-name heuristics confer no authority. No replay imports grants.
