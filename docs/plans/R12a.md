# R12a — Live capability grant records

Explicit authority is a validated record, not an inferred answer in a transcript. This row
implements the live core registry, enforcement, audit events and migration of existing TUI
standing answers. Richer approval UI, age/hit-count/why displays and child delegation filtering
remain R12b, R12c and R12d respectively.

## API and scope

`PermissionGrantRegistry` is an optional trusted `AgentConfig.permissionGrants` / CLI
`AgentExtras.permissionGrants` instance. Its `grant`, `revoke`, `clear`, `list` and lifecycle
methods operate on in-memory records only. `PermissionGrantSchema` strictly validates:

```ts
{
  id, subject, createdAt,
  operation: { tool, class?, commandPrefix? },
  resource: "*" | { kind: "path-prefix", path: absolutePath },
  constraints: { cwd?: absolutePath },
  duration: { kind: "session" | "task", id },
  delegable: boolean,
  decision: "allow" | "deny"
}
```

The registry stamps IDs/time, clones inputs/outputs and requires the current subject and duration
ID. `subject` identifies the live shared authorization group, not an authenticated principal.
Operations match an exact tool name and optional permission class. Shell prefixes reuse R12e's
bounded literal argv matcher, including its foreground and unsupported-syntax restrictions.
There are no string globs, name heuristics, transcript-derived rules or MCP-hint authority.

Path resources require nonempty declared paths, at most 128, with **every** path lexically inside
the absolute resource prefix. Optional cwd constraints match the resolved cwd exactly. Unknown
constraints/durations reject; relative resource/cwd scopes reject instead of following a moved
working directory. These are advisory permission scopes over trusted tool declarations, not
symlink containment, executable attestation or an OS boundary. Shell calls declare no paths and
cannot satisfy a path grant. Sandbox containment remains independently enforced.

## Enforcement and lifetime

- Core consults grants only when the configured base policy returns `ask`. An explicit base
  allow or deny keeps its meaning. First matching live grant wins; changing that answer means
  explicitly revoking it. Standing deny is represented and enforced too.
- TUI standing answers become session records with `resource: "*"` and exact tool operation,
  preserving their explicitly broad scope. Separate sandbox-escalation and MCP-definition
  consent cannot use or mint grants. R5d consent still cannot be bypassed with blanket authority.
- A root run binds the registry to its session ID and a fresh opaque task ID. Task grants expire
  when that run ends, including abort/error. Session grants survive same-ID continuation while
  the same registry remains alive, but never process restart or a fresh registry.
- `/new`, successful fork, changing session and undo revoke the old conversation's records.
  This intentionally fixes the previous controller-wide map leaking advertised session grants
  across conversations. A remembered answer queued before reset cannot recreate stale authority.
  Same-session pause/resume is not a new conversation and retains session grants.
- Children explicitly share the same group today. `delegable` is recorded but **not filtered**
  until R12d, including records with `delegable: false`; no per-child isolation is claimed.
  Already-running sessions capture their grant session and cannot adopt another root session's
  grants after the registry switches. Explicit base authority remains unchanged. Host-configured
  nested/orphan descendant lifecycle is not a principal/delegation boundary in this row.
- Simultaneous root runs using one registry refuse rather than switching its live context.
  Independent root runs require separate registries. Host code can explicitly construct/change
  registries; that is trusted SDK authority, not input from the model or repo.

## Audit and bounds

`permission.granted` contains the exact validated record; `permission.revoked` names its ID,
subject and reason. Both render in verbose output and round-trip through the canonical event
schema. Tools cannot emit either authority event. Recorded events are evidence, never an
installation source: resume/fork only restores conversation, not grants.

Core flushes pending changes before authorization, after interactive answers and before terminal
session close. No dispatch follows a failed permission-audit append. A failed append remains at
the queue head; shared parent/child drains serialize. Idle resets/transitions acknowledge their
effect immediately and queue revocations for the next active session, rather than appending
after `session.end`. If the process exits first, no synthetic durable receipt is claimed. The
closing process discards its authority; restarting does not replay the queued or historical data.

Defaults: 256 live grants, 1,024 pending audit events; trusted constructor overrides are positive
integers capped at 4,096. Registry/queue saturation throws, never evicts live grants or silently
drops an audit change. Queue overflow blocks grant-derived authority until successful flush and
explicit reset; a caller may instead discard the whole registry. Each name/ID is at most 256
characters, each path 4,096; command prefixes retain R12e's 128-word / 16 KiB bounds. A flush
processes its bounded initial queue, refuses concurrent extra changes before dispatch, and retains
any unrecorded change. SDK `decide` is a matcher; the core runtime supplies the audit-before-use
guarantee. The registry and host callbacks are not a sandbox for arbitrary SDK code.

## Verification

Tests cover strict schemas, lexical all-path matching, argv scopes, missing/empty paths, explicit
base decisions, caps, append failures, concurrent drains, revocation before the next call, task
expiry, actual TUI transitions and same-session retention, real child sharing without delegation
claims, and refusal to restore authority from grant-bearing logs. A fake provider drives the
shipped CLI builder and real inert shell commands through a narrow live grant. Exact-head
build/typecheck/full suite, restored mutations, one independent review and three-platform CI
receipts are recorded with the closing PR.
