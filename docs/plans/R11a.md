# R11a — additive net permission and sandbox composition

`net` is a new, distinct permission class. It defaults to ask (unattended denial), participates
in explicit rules and live scoped/child grant records, and maps to R13c's existing network
expansion category. Legacy `network` stays separate and retains its existing behavior. No
tool-name, model-text or MCP hint inference supplies authority. There is no fetch tool in this
row; R11b owns that implementation.

The runtime checks the selected live sandbox policy before a net tool body or expansion
dispatch bookkeeping, even for trusted tools declaring sandbox compatibility. A non-none
policy without `network: true` refuses execution. CLI `--sandbox-network` and boolean config
`sandboxNetwork` expose that explicit SDK policy. They do not grant net permission; `--allow
net` and YOLO do not enable sandbox network. Mode none has no OS sandbox enforcement.

An independently established policy refusal retains the existing fresh, one-invocation
sandbox-escalation escape. Explicit approval executes outside the sandbox; it does not enable
network inside it. Standing/scoped grants cannot answer that separate consent. Without a
handler it fails closed. Parent sandbox narrowing prevents children enabling forbidden network.

This is trusted-tool composition, not containment of arbitrary host JavaScript. Existing
provider traffic, MCP server processes, and undeclared behavior do not become controlled merely
by adding a class. Destinations and other effects remain unknown; no hostname scope is claimed.

> **APPROVE.** No material findings in the R11a diff against origin/main. Seven related test files pass and typecheck is clean across all four packages.
>
> **What I verified against the contract in docs/plans/R11a.md:**
>
> - **Runtime gate before body and category accounting.** The net gate sits at `packages/core/src/tool-execution.ts:378-381`, inside the deferred command, ahead of the expansion `dispatched` call, the restriction binding, and the tool body. It runs under the async-local policy set by withSandboxPolicy, and the process providers invoke the command inside that context, so the gate cannot be skipped by a provider wrapper. Mode none passes an undefined policy, so the gate is inert there.
> - **Sandbox network independent from permission and YOLO.** The flag flows program.ts → loadRunConfig → runCommand → buildAgent → buildSandbox. buildPermissionPolicy never reads it, and buildSandbox never reads allow or yolo. The core test confirms blanket allow still trips the gate, and network true without permission still asks.
> - **Separate one-time escape.** The escalation path calls the original command through outsideSandbox, which clears the policy so the gate passes exactly once. Grants refuse to remember sandbox-escalation requests, and the TUI scope helper throws on them.
> - **Legacy network compatibility.** The gate keys only on class net. Legacy network tools run under the prepared policy unchanged, and rules for one class do not match the other.
> - **Fresh external expansion.** Class net maps to the existing network surface at `packages/core/src/external-expansion.ts:56`. A denied sandbox invocation does not open the category because the gate throws before dispatch bookkeeping.
> - **Child narrowing and grants.** The subagent check at `packages/core/src/tools/subagent.ts:229` blocks a child enabling network when the parent policy lacks it. Grants use the shared PermissionClass schema, so net grants filter through the existing child view without new code.
> - **No isolation overclaims.** README and the contract state that none mode has no OS sandbox and that in-process JavaScript is not contained. The CLI test asserts none mode yields no runtime policy.
>
> **Optional polish, not blocking:**
>
> - `--sandbox-network` is a bare boolean with no negating flag. A config file setting sandboxNetwork to true cannot be overridden to false from the command line for one run. Other boolean options in program.ts follow the same pattern, so this is consistent, but a `--no-sandbox-network` option would close the gap.
> - In `packages/cli/src/agent-builder.ts:107`, none mode with network true still forwards network true to the none provider. It is harmless since no policy is established, but dropping the grant in none mode would make the config object match the documented behavior more literally.

The wrapper statement above applies to the exercised trusted provider implementations, not a
security guarantee against arbitrary SDK host JavaScript. Both optional notes remain end-of-roadmap
polish; current explicit metadata propagation and boolean flag conventions stay compatible.
