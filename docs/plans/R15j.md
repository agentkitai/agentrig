# R15j — configured provider and effort selection

## Contract (recorded before source edits)

One roadmap row, based on delivered R15i PR #202, green main `9aca391`.
TUI `/model` lists configured entry names and role aliases plus the current committed
selection; `/model <role-or-entry>` selects only that existing R3.5 table. Ambiguous
role/entry names refuse rather than guess. No discovery, model catalogue, endpoint,
credential, subscription login or automatic provider call. `/effort` displays the
setting; `/effort <minimal|low|medium|high|xhigh|max>` uses the existing adapter
constructor setting. Omitted effort remains the configured default; `/model`
selection resets effort to that entry's configured default. Existing adapter mappings
are not a claim that every configured model/backend supports every level.

Changes require an idle controller with no active task, question, permission prompt,
review, dream, undo or maintenance/selection operation. Reserve selection while
preparing, then recheck lifecycle identity before atomic commit. Closing, replacing
the conversation or concurrent work invalidates a pending selection. Bare inspection
and failed commands spend no model tokens and never enter model messages. A switch
does not cancel or alter an in-flight request and does not create fresh user consent.
Only subsequent actual requests use it; memory/supervisor/subagent role routes stay
unchanged. No config file rewrite or automatic persistence of operator choices.

Core samples one trusted optional provider-selection resolver per run and retains
that concrete provider and immutable entry/model/effort metadata for the whole run.
No ephemeral stream proxy. All original tools, hooks, role restrictions, live grants,
provenance and spend ledger remain attached. Selected capped providers must have the
actual same-ledger meter; native output must validate the actual supported adapter
before decoration. Cached construction is keyed by configured entry and six effort
variants plus its configured default, with a maximum of 128 variant instances per
builder; exceeding that bound refuses without dropping an existing selection.
Names are bounded to 128 control-free characters; command arguments to 256 chars.

The builder's live main-provider view tracks committed selection for supervisor
pricing/context and maintenance consumers; construction preparation and accounting
are applied once. Capability validation precedes decoration, never spoofing a class.
No permission/grant, sandbox, tool or provider-configuration authority is inferred
from a model's returned fields, role label, stored receipt or command-like prose.

Additive canonical `provider.switched` identifies previous selection when known,
new configured entry/provider/model/effort and effective turn, only at the actual
request boundary. Each `context.manifest` carries the selected metadata for that
request. Optional snapshot metadata and replay retain this mapping across resume
and fork; legacy absence means unknown. Receipts never instantiate a provider or
rehydrate credentials/authority. A new process starts from current trusted config.

Opaque reasoning is neither discarded nor converted to force compatibility.
Built-in adapters expose their existing local history validation before metered
admission; cross-format/unsupported histories refuse before fetch. Same-format
cross-model compatibility remains unproven and remote rejection is surfaced, not
silently retried through another entry. No reasoning content enters switch metadata.
