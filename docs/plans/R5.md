# R5 implementation plan — extensions and packages

**Status:** guidance for the `/topic R5` train. The roadmap row text in `docs/ROADMAP.md` is the
contract and its acceptance paragraph is the judge; this plan fixes the design choices a builder
would otherwise make mid-implementation. A builder that departs from this plan records the
departure in the PR body under `## Plan departures` with the reason; a departure from the *row*
still goes through the deviation gate. Where this plan and the row disagree, the row wins and the
plan is wrong.

Written 2026-09-04 against main `aad81ee`, before R4 landed. If R4 changed a seam named here
(hooks, `AgentConfig`, the TUI controller), the code wins and the builder notes the drift.

## 0. What exists today, and what each row builds on

| Seam | Where | Facts the design relies on |
|---|---|---|
| Hooks | `packages/core/src/hooks.ts` | Seven points; `Hook {point, id?, timeoutMs?, handler}`; the runner isolates every handler (copy of the context, timeout, throw → non-fatal `error` event, `modify` patches validated). An extension hook is just a `Hook` pushed onto the list `createAgent` receives. |
| Tools | `packages/core/src/tool.ts`, `tools/index.ts` | `Tool {name, description, inputSchema, permission, paths?, jsonSchema?, execute}`; `AnyTool` is what registries hold. Tool names are `^[a-zA-Z0-9_-]{1,64}$` (the MCP adapter enforces it). `TOOL_EMIT_SOURCES` in `events.ts` ties authority events to ONE tool name each (`plan.updated` → `update_plan`, `subagent.*` → `subagent`, `skill.used` → `skill`). |
| Assembly | `packages/cli/src/agent-builder.ts` `buildAgent` | Order: provider → memory → MCP (`connectServers`) → sandbox/permissions → hooks (`extras.extraHooks` + memory hooks) → `discoverSkills` → `tools = [...builtins, ...memory, ...mcp, skill?, subagent?]` → `createAgent`. Returns `BuiltAgent {agent, provider, tools, skills, mcp, …}`. Children rebuild tools through `childTools()`. |
| TUI commands | `packages/cli/src/tui/commands.ts`, `tui/controller.ts` | `parseCommand` is pure; `COMMANDS` is a static table and the `/help` source of truth; an unknown `/word` becomes `{kind:"skill"}` and the controller resolves it against the loaded catalogue (issue #62), else `unknown` with did-you-mean. |

| Skill roots | `packages/cli/src/config.ts` (#61) | explicit `--skills` → `<trusted root>/.agentrig/skills` (only when trusted) → `~/.agentrig/skills` (only when `userStateSafe`). Deduped. |
| Trust | `packages/cli/src/trust.ts` (R1d) | `resolveProjectTrust` gates `AGENTS.md`, project config and project skills. `--trust` is per-invocation. Home-inside-repo disables user state. |

## 1. R5a — Extension API in core

### Shape of an extension

- A file `<name>.mjs` under `.agentrig/extensions/` (project, trust-gated) or a path given with
  `--extension <path>` (repeatable; explicit, always loaded). The extension's **name is the file
  basename** without `.mjs`, validated against `^[a-z0-9][a-z0-9_-]{0,63}$`; anything else is
  rejected before import. No home directory root: the row names two sources and only two.
- An optional sidecar manifest `<name>.json` beside the module (`{ "name", "version",
  "apiVersion": 1 }`). R5a reads it when present and rejects a mismatch between manifest name
  and file name; R5e makes it mandatory and strict. Designing the sidecar now is what lets R5e
  validate *before* import: a manifest inside the module can only be read by executing the module.
- The module exports `activate(ctx)` (named export; a default export that is a function is
  accepted as an alias). Anything else is an activation failure.
- `activate` runs **once per process, before the session starts**, under a 10 s timeout, and
  registration is only legal while it runs: the context is sealed when `activate` settles, and a
  later `registerTool`/`registerCommand`/`hooks.on` throws. That closes the "register a tool from
  inside a hook after the permission table was built" hole by construction.

### `ExtensionContext` (new file `packages/core/src/extensions.ts`)

```ts
interface ExtensionContext {
  readonly name: string;
  readonly session: { readonly cwd: string; readonly provider: { id: string; model: string } };
  hooks: { on(point: HookPoint, handler: Hook["handler"], opts?: { timeoutMs?: number }): void };
  registerTool(tool: AnyTool): void;
  registerCommand(cmd: { name: string; args?: string; summary: string; run(args: string, io: CommandIo): Promise<void> | void }): void;
  log(message: string): void;
}
```

- `session` is a frozen plain object: cwd and the provider's id/model string. No session id
  (the session does not exist yet), no store, no provider object, no `process.env` mirror. That is
  the whole "read-only session info" surface; R5b pins its key set.
- `hooks.on` pushes a `Hook` with `id: "ext:<name>:<point>"`. A per-hook `timeoutMs` may only
  *lower* the runner default; a larger value is clamped and reported once. The seven points
  include `session_end`, which is what a memory-style extension needs.
- `registerTool` validates: name regex; not a builtin name; not `skill`, `subagent`,
  `update_plan`, `read_output`; not an MCP name (`mcp__` prefix reserved); not already registered
  by another extension. Any collision fails **the whole extension** (R5b's atomicity), because a
  tool named `update_plan` from an extension would inherit `plan.updated` emit authority through
  `TOOL_EMIT_SOURCES`. This check is security-relevant: name the mutant.
- `registerCommand` validates the name against `^[a-z][a-z0-9-]{0,31}$`, rejects any name in the
  TUI's built-in `COMMANDS` table and any alias `parseCommand` accepts (`?`, `stop`, `trace`,
  `exit`…), and rejects duplicates across extensions. `io` is `{ print(text: string): void }`;
  a command never gets the controller.
- `log` routes to the CLI notice channel (the same `onNotice` MCP uses). Not an event.

### Loader

```ts
loadExtensions(opts: {
  paths: string[];                // resolved .mjs paths, project dir already trust-filtered by the CLI
  session: ExtensionContext["session"];
  builtinToolNames: ReadonlySet<string>;
  reservedCommandNames: ReadonlySet<string>;
  now?: () => number;
}): Promise<{ loaded: LoadedExtension[]; failed: FailedExtension[] }>
```

- `LoadedExtension { name, path, hooks: Hook[], tools: AnyTool[], commands: ExtensionCommand[], surfaces: {hooks: HookPoint[], tools: string[], commands: string[]} }`.
- `FailedExtension { name, path, phase: "manifest" | "import" | "activate", message }`.
- Import with `import(pathToFileURL(path).href)`. On Windows a bare path is not a valid
  specifier; this has bitten before. Node caches modules by URL, so two loads of the same path in
  one process return the same module: tests use distinct tmp paths, never a rewritten file.
- Partial registrations of a failed extension are discarded: registrations are collected into a
  draft and committed only when `activate` resolves without throwing.
- `loadExtensions` does no I/O beyond reading the manifest and importing; discovery of
  `.agentrig/extensions/*.mjs` (sorted, `lstat`, no symlinks, ≤ 32 files) is `discoverExtensions(root)`
  in the same file, called by the CLI.

### Wiring in `buildAgent`

1. After MCP connect and before hooks: `paths = [...explicit, ...(trusted ? discoverExtensions(projectRoot) : [])]`.
2. `loadExtensions(...)`; collision checks run against the final builtin + memory + MCP tool
   list, so an extension cannot shadow an MCP tool either.
3. `hooks.push(...ext.hooks)` (after memory hooks: an extension sees the session the way a user
   would, memory having already run); `tools.push(...ext.tools)`; children inherit extension
   **tools** through `childTools()` but not hooks or commands — a child's hooks fire in the parent,
   which already has them.
4. `createAgent({ ..., extensions: { loaded, failed } })` — a schema-added `AgentConfig` field,
   so core emits the events from inside the session (the CLI cannot).
5. `BuiltAgent.commands: ExtensionCommand[]` for the TUI.

### Events

- `extension.loaded { name, path, surfaces: { hooks: string[], tools: string[], commands: string[] } }`
  emitted by the loop right after `session.start` (and after `session.resume`), one per loaded
  extension, in load order.
- `extension.error { name, path, phase: "manifest" | "import" | "activate" | "hook" | "tool", message }`
  emitted right after `session.start` for each `failed` entry (R5b adds the runtime phases).
- Both get a `renderEvent` case (`ext name +hooks:pre_tool,post_tool +tools:x +commands:y`) and
  belong to the loop only: **not** added to `TOOL_EMITTABLE_EVENTS`.

### TUI

- `parseCommand` stays pure and unchanged. The controller gets `setCommands(cmds)`; in the
  `unknown`/`skill` fallthrough it checks extension commands **before** skills (precedence:
  built-in > extension > skill), and `/help` appends an `extensions:` section from the same list.
  A skill shadowed by an extension command is reported once at load through the notice channel.
- A command's `run` is awaited inside a try/catch; a throw prints `extension <name>: <message>`
  and disables that extension's commands for the rest of the process (see R5b; the CLI has no
  emit path, so this one is a notice, not an event — state it in STATUS).

### Tests (R5a)

Fixture: `packages/core/test/fixtures/extensions/hello.mjs` registering a `hello` command, a
`hello_tool` tool, and a `pre_tool` hook that denies `bash` when the command contains `rm -rf`.

- `extensions.test.ts` (core): loads the fixture; `surfaces` match; sealed context throws after
  activate; name regex rejections; collision with `update_plan`, with a builtin, with an MCP name,
  with another extension — each fails the whole extension and registers nothing; manifest/file
  name mismatch rejected; missing `activate` → `phase: "import"`; 10 s timeout → `phase: "activate"`
  (fake clock).
- `events.test.ts`: zod round-trip for both events; `renderEvent` cases.
- `agent.test.ts`: `extension.loaded` follows `session.start` in `seq` order; a fake provider
  calling `bash rm -rf` is denied by the fixture hook (`tool.denied` in the log) — this is the
  row's "gates a tool call".
- `tui.test.ts` (cli): controller with the fixture's commands: `/hello` prints; `/help` lists it;

- `run-flags.test.ts`: `--extension` repeatable; project extensions not loaded when untrusted

**Named mutants:** (1) drop the `update_plan`/builtin collision check; (2) drop the seal (late
`registerTool` succeeds); (3) drop the trust filter on the project directory; (4) emit

## 2. R5b — Failure isolation and no ambient credentials

- **Activation** failures are already atomic from R5a. R5b pins the three phases with a fixture
  per phase (`throws.mjs`, `rejects.mjs`, `hangs.mjs`) and asserts the session finishes `done`
  with the `extension.error` event in the log and nothing else from that extension present.
- **Runtime unload.** Each extension's hooks and tools are wrapped by core in `createAgent`
  (`wrapExtension(ext, emit)`), which is where `emit` is available:
  - A hook handler throw → the runner already isolates it; the wrapper additionally marks the
    extension `disabled`, emits `extension.error {phase:"hook", message}` once, and every later
    hook of that extension returns `continue` without calling the handler.
  - A tool `execute` throw (an unexpected failure; `isError` results are normal) → the wrapper
    returns `{ isError: true, display: "extension <name> unloaded: <message>" }`, emits
    `extension.error {phase:"tool"}`, and every later call of that extension's tools returns the
    same refusal without executing. Tool *definitions* stay in the model's list for the session
    (the request shape is fixed at session start); the refusal text names the fix (restart).
  - Disabling is per extension, not per surface: a throwing hook also disables the tools.
- **No ambient credentials.** The context exposes no provider object, no store, no `onAsk`, no
  budget, no env. Test: `Object.keys(ctx)` and `Object.keys(ctx.session)` pinned exactly;
  `ctx.session` and `ctx` are frozen (`Object.isFrozen`); assigning throws in strict mode.
  Say plainly in STATUS what this does NOT do: an extension is in-process Node code and can read
  `process.env` or the token file if it wants. The API surface is the contract; the trust gate is
  the boundary. A `vm`/worker sandbox is a renunciation (pi's position), recorded, revisit if
  R5c packages ever get third-party authors.
- Acceptance mutant: removing the wrapper's try/catch fails the crash test (a fixture whose
  `pre_tool` hook throws on the second call; the session must still reach `session.end done`).

## 3. R5c — Packages

The row's package column says `cli`; CLAUDE.md says logic belongs in a package. The installer's
logic (tar reading, validation, hashing, discovery) lives in core `packages/core/src/packages.ts`
and the CLI command is wiring. That is the repository rule, not a deviation.

### Source forms and extraction

- `agentrig package add <src>` accepts a directory or a `.tgz`/`.tar.gz` file (npm `pack` output,
  entries prefixed `package/`). No registry, no URL, no git: distribution is by file (renunciation
  stands).
- **Own tar reader**, no dependency: ustar/pax headers, gzip through `node:zlib`. Roughly 150
  lines and fully deterministic, versus a `tar` dependency the Windows CI leg would also have to
  trust. It accepts regular files and directories only; **symlinks, hardlinks, device entries,
  absolute paths, `..` components, and paths outside `package/` are refusals** that abort the
  install with the offending entry named. Size caps: 20 MiB compressed, 100 MiB extracted, 2000
  entries, 4 KiB path. The reader is a pure function over bytes, which makes the bomb tests cheap.
- Extraction goes to a temp directory under `.agentrig/packages/.staging-<random>/`, validated
  in full, then renamed into place. Nothing is executed at any point, ever. There is no code path
  that spawns a process in this module; the test asserts `child_process` is not imported by it.

### Manifest and refusal

- `package.json` is required: `name` (npm-valid, no scope slashes in the directory name: `@a/b`
  installs as `a__b`), `version`, optional `agentrig: { apiVersion: 1 }`. A `scripts` object
  containing **any** of `preinstall`, `install`, `postinstall`, `prepare`, `prepublish`,
  `prepublishOnly`, `prepack`, `postpack` → refused, naming the key. A non-empty `dependencies`
  or a `bin` field is also refused: nothing ever installs them, so a package that needs them
  cannot work, and saying so at install beats a broken extension at session start. The acceptance fixture is a tarball with `postinstall`; nothing is
  written on refusal (assert the packages directory is unchanged, staging removed).
- Only `extensions/`, `skills/`, `prompts/`, `package.json`, `README*`, `LICENSE*` are copied;
  anything else in the archive is listed as ignored in the command's output, not copied.
- Integrity: `sha256` over `sorted(relative path)\0size\0sha256(bytes)` per copied file, recorded
  in `.agentrig/packages/<name>/.agentrig-package.json` `{ name, version, source, installedAt,
  sha256, files: [...] }`. On every load, the recorded hash is recomputed; a mismatch refuses the
  whole package with "re-run `agentrig package add`", so a hand-edited or repo-planted package
  is never partially trusted.
- `agentrig package add` over an existing name refuses unless `--replace`; `--replace` removes
  the old directory only after the new one is staged and validated.

### Discovery precedence (also the R5e order)

`explicit flags` > `<trusted root>/.agentrig/skills|extensions` > packages, alphabetical by
directory name > `~/.agentrig/skills`. Packages are repo content under `.agentrig/`, so they load
only when the project is trusted, exactly like project skills. `prompts/*.md` are copied and
listed by the command but **not injected**: nothing consumes prompt packs yet (R6g is the
consumer) and injecting unread text into the system prompt is not this row's job. Say so in STATUS.

### Tests (R5c)

Fixtures built by a test helper that writes tarballs from an in-memory file list (no `tar`
binary in tests): good package; `postinstall` package; `..` entry; symlink entry; absolute
entry; oversize; duplicate name; hash tamper (edit one byte after install → load refuses).
`doctor` gains one line per package (name, version, hash ok/mismatch).

**Named mutants:** (1) drop the scripts check (acceptance); (2) drop the symlink refusal; (3)
drop the hash verification on load; (4) copy before validation completes (a `..` entry after
1000 good ones must leave nothing behind).

## 4. R5d — MCP tool-definition pinning

- **Canonical hash.** Per tool: `sha256(canonicalJson({name, description, inputSchema}))` with
  keys sorted recursively and strings as-is (no sanitisation before hashing: what changed is
  what the server sent). Per server: `sha256` of the sorted per-tool hashes joined by `\n`.
- **Pin store** `~/.agentrig/mcp-pins.json`, strict zod schema `{ version: 1, servers: {
  [key]: { toolsHash, tools: { [toolName]: hash }, pinnedAt } } }` where `key =
  sha256(name\0command\0args.join("\0"))` — a config that swaps the command under the same
  server name is a new server, not a changed one. User state, so under home-inside-repo
  (`userStateSafe === false`) there is no store: every session then treats every tool as
  changed and prompts. Fail closed, never fail silent.
- **First use** records silently and emits `mcp.pin { server, status: "recorded", tools:
  string[] }`. **Changed** tools: at connect, compute the diff per tool (`added`, `removed`,
  `description changed`, `schema: gained field x`, `schema: type of y changed`) and emit
  `mcp.pin { server, status: "changed", tools, summary }`. Removed tools are just gone;
  unchanged tools run as before; **only the changed and added ones are gated**.
- **The gate** copies R2c's sandbox escalation exactly: in the loop, before the normal
  permission decision for a gated tool, a `permission.request` with `origin: "mcp-pin"` and a
  `reason` carrying the one-line diff goes **straight to `onAsk`**, never through the policy, so
  `--yolo` cannot auto-accept a changed definition; headless with no `onAsk` denies. `allow`
  updates the pin store for that tool only and emits `mcp.pin {status:"accepted"}`; `deny` emits
  `tool.denied` and `mcp.pin {status:"rejected"}` and asks again on the next call (a standing
  answer would defeat the point). The seam is `AgentConfig.toolGates?: ToolGate[]` with
  `ToolGate { applies(toolName): string | undefined /* reason */; accept(toolName): Promise<void> }`
  — schema-added, generic enough that R12's grants can reuse it, small enough to review.
- `PermissionRequest.reason?: string` is a new optional field (schema-added) so the TUI prompt
  can show the diff; the TUI renders `origin: "mcp-pin"` distinctly ("tool definition changed —
  run it?") the way it renders sandbox escalation.
- `doctor --probe` is R10d; R5d adds nothing to doctor beyond listing pinned servers.

### Tests (R5d)

Fake MCP server (the existing test harness spawns a scripted stdio server): first session
records; second session with a changed description → `mcp.pin changed` at connect, the changed
tool's first call produces `permission.request origin:"mcp-pin"` with the diff in `reason`,
unchanged tools of the same server run without a prompt; `--yolo` still prompts (`RulePolicy`
fallback `allow` + no `onAsk` → denied, with the `mcp.pin rejected` event); `allow` persists and
the third session is silent; store file with an unknown version refuses to load and everything
prompts; home-inside-repo → no store, prompts.

**Named mutants:** (1) route the pin ask through the policy (yolo test fails); (2) key the store
by name only (command-swap test fails); (3) hash after sanitisation (a description that changes
only in a control character must still count as changed); (4) accept persists the whole server
instead of the one tool (a second changed tool must still prompt).

## 5. R5e — Fail-closed manifests

Three versioned schemas in `packages/core/src/manifests.ts`, all `.strict()`:

- `SkillFrontmatterV1`: `name`, `description`, optional `version`, `license`, `compatibility`,
  `metadata` (string record), `schema: 1`. The agentskills.io field `allowed-tools` is **known and
  rejected** with "AgentRig does not honour allowed-tools; remove it" — the row's "unknown
  security-relevant field" case made concrete: a permission-shaped claim we cannot enforce must
  not load silently. Any other unknown key rejects the skill. A file with **no** frontmatter block
  keeps today's fallbacks (a skill is text and carries no permissions to widen); a block that
  exists and fails the schema rejects the skill and reports it through `onError`. The hand-rolled
  scanner stays (no YAML dependency) but gains: duplicate keys → reject; a value with a leading
  `-` or `[` → reject with "lists are not supported".
- `ExtensionManifestV1` (`<name>.json`, now mandatory): `name`, `version`, `apiVersion: 1`,
  `surfaces: ("hooks"|"tools"|"commands")[]` — and `loadExtensions` refuses a registration outside
  the declared surfaces, so the manifest is a capability declaration a reviewer can read without
  running the code. `extension.loaded.surfaces` already carries what was actually registered.
- `PackageManifestV1` — the `package.json` subset from R5c plus `agentrig.apiVersion`, strict on
  the `agentrig` object only (npm `package.json` legitimately carries many keys).
- **Duplicates.** Across roots: the documented order (§3), first wins, reported (exists today for
  skills; extended to extensions and packages). **At equal precedence — the same root, or two
  packages — a duplicate is an error and neither loads**, reported with both paths. Case-insensitive
  keys, so `Foo.md` and `foo/SKILL.md` in one root collide. This replaces today's silent
  first-by-iteration within a root.
- Every existing checked-in skill under `.agentrig/skills` must still load: the core test that
  guards the repo's own skills (STATUS "First checked-in skill") is the regression net.

**Named mutants:** (1) `.strict()` removed on the extension manifest (a manifest with
`permissions: "*"` must reject); (2) `allowed-tools` accepted; (3) equal-precedence duplicate
falls back to first-wins; (4) a registration outside declared `surfaces` accepted.

## 6. Cross-cutting

- **Events added:** `extension.loaded`, `extension.error`, `mcp.pin`; field added:
  `PermissionRequest.reason`. Each: zod variant, `renderEvent`, test. None tool-emittable.
- **`AgentConfig` fields added:** `extensions`, `toolGates`. `BuiltAgent` gains `commands`.
- **Config keys** (`packages/cli/src/config.ts`): `extensions: string[]`, `extensionDiscovery:
  boolean` (default on, mirrors `skillDiscovery`), `packages: boolean` (default on). Flags:
  `--extension <path>` (repeatable), `--no-extension-discovery`, `--no-packages`.
- **`doctor`:** one line per extension (loaded/failed + phase), per package (hash ok/mismatch),
  per MCP server (pinned/changed).
- **Trust:** project extensions and packages load only when trusted; `--extension` and
  `--trust` are the explicit overrides. A test per row proves the untrusted path loads nothing.
- **Windows:** `pathToFileURL` for imports; path separators in package file lists normalised to
  `/` before hashing so a package installed on Windows verifies on macOS.
- **Docs:** each row's PR updates STATUS with the decisions above that it actually made, marks
  its row `*(done)*`, and adds a short "Extensions" section to README (how to write one, the
  fixture as the example).

## 7. Order and size

R5a → R5b → R5c → R5d → R5e, as the roadmap lists them. R5a is the large one (core API, loop
events, TUI wiring, ~600 lines with tests); R5b is small on top of it; R5c is medium and
self-contained; R5d touches the loop's permission path and needs the most careful review; R5e is
mostly schema and a behaviour change in the skills loader. A builder that finishes R5a and R5b in
one PR has widened the row: keep them separate, R5b's fixtures are its own proof.

## 8. Pitfalls a builder will hit

- `import()` caches by URL: never mutate a fixture file between two loads in one test process.
- ESM under vitest resolves workspace packages to `src`; a fixture extension importing
  `@agentkitai/agentrig-core` works in tests but not from a built CLI unless the package is
  resolvable from the extension's directory. The fixture imports nothing; say in README that an
  extension should import nothing from the harness and treat `ctx` as its whole API.
- The hook runner clones the context per hook; an extension that keeps state must keep it in its
  own closure, not on `ctx`.
- The TUI test harness (`makeController` in `packages/cli/test/tui.test.ts`) drives the controller
  with scripted `ModelEvent[]`; no screen. A command test asserts on `snapshot().lines`.
- Skills' `sanitizeLine` bounds names to 80 and descriptions to 200 before they reach the system
  prompt; extension names and command summaries go through the same function.
- Tarball fixtures: build them in the test with the helper, commit no binary fixtures.
- macOS: wrap tmpdir fixtures in `realpath` (`/var` → `/private/var`); the R2/R3 trains hit this.
