# H1 — Tool effects cross the sandbox boundary

The direct Node writes in `write_file` and `edit_file` bypassed the process sandbox even when
ordinary permissions allowed the tool only inside a sandbox. H1 keeps the two decisions separate.

- Built-in file mutation uses a small filesystem broker. Without an active boundary it retains
  Node filesystem behavior. Under Docker/Seatbelt, bytes go over stdin to a fixed shell program
  running inside the actual OS boundary; paths are argv data. Read-only and lexical outside-cwd
  writes are refused before launch, and the OS checks the final filesystem operation, including
  parent symlinks. Docker uses the caller's UID/GID and keeps stdin open for the broker.
- `Tool.sandbox: "compatible"` is an explicit trusted SDK registration contract, not a model or
  MCP annotation. Core builtins declare it only when they read, update internal session state, or
  use the process/file broker. Unmarked tools, including memory tools and subagents, are refused
  inside an enforcing mode and can run only through the existing one-call escalation approval.
  Tool names and read permissions cannot manufacture compatibility.
- Host hooks are refused at agent construction rather than silently skipped: skipping a
  permission hook could remove a restriction. This includes ingest/dream-on-end. CLI MCP startup
  is refused before reading the server config or launching any server in an enforcing mode.
- Providers, SDK registration code, session persistence and prompt construction are trusted host
  operations. H1 does not claim to isolate arbitrary JavaScript loaded into the harness process.
  A custom SDK provider is responsible for implementing its own enforcement. The built-in none
  provider refuses an enforcing mode rather than quietly treating it as none.

Validation: scripted models drive the actual file and memory tools through concrete providers;
live Docker and (where available) Seatbelt exercise successful inside writes and symlink escape
refusal. Permission denial and explicit one-shot escalation have separate assertions. Core's
pre-existing fake-provider tests still validate the generic seam, not OS enforcement. Full-suite
validation uses a clean checkout because the nested-worktree map bug is the separate H2 row.

Future compatibility work must bring its own broker and real-effect tests before marking memory,
MCP, hooks or subagents compatible. Unsupported features remain explicit refusals in the meantime.
