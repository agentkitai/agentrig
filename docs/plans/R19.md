## Target layers

R19 establishes three target layers; this section is a boundary to migrate toward,
not a claim that the repository already has it.

1. **Harness (core + generic CLI).** Agent loop, sessions/event log/resume,
   tools/permissions/grants/sandbox, hooks including spawn hooks, agent roles with
   provider binding, skills with includes/assets/flags, extensions/packages that can
   add CLI commands and config, providers/spend/concurrency, memory and supervisor.
   It knows nothing about PRs, reviewers, landers, trains or rows.
2. **Ship pack (workflow extension).** Roles conductor/builder/fixer/reviewer/lander/
   arbiter; skills plus `SHIPPING-WORKFLOW` with shared sections as includes; scripts
   for reviewer adapters, verdict schema, finding index and comment posting; its own
   config namespace (reviewer slots, declared checks, reviewer homes); its hooks
   (dispatch record for #539 and merge guard); and its own instruction-contract and
   script-test CI lane.
3. **Train (application).** Queue/active/done/halted, STOP/PAUSE, a row schema with
   pluggable pre-check/prompt/receipt/verify stages, per-row usage rollup, and launcher
   environments/profiles.

## Missing generic mechanisms

The harness must gain exactly these six generic mechanisms:

1. Spawn hooks (`pre_spawn`/`post_spawn`) with exact task text, role and parent.
2. Agent roles bound to a named provider entry, replacing `builderProvider`.
3. Skill includes, bundled assets and flags, for example `fresh-session`.
4. Packs that contribute CLI commands and a namespaced config schema, with a
   backward-compatible reader for today's top-level keys.
5. A small public API for building a role's provider, resolving child environments
   and resolving project checks.
6. A spawn-log query API over the immutable event log.

### R19a implementation slices (partial; row acceptance is not complete)

The authorized first coherent PR implements only spawn hooks and the spawn-log API:

- Extension hooks `pre_spawn` / `post_spawn` receive `ctx.spawn` with exact submitted
  `task`, `parent` session ID, and the selected role's name/origin/hash/declared tools,
  model-role and delegable flag when named. Post adds `childId`. Snapshots are frozen;
  this is a gate/notification seam, not a task or role rewrite seam.
- Pre runs after existing input/capability/cap checks, before child configuration,
  ID allocation and launch. Only `continue` / `deny` are valid. Errors, timeouts and
  unsupported results fail closed. Shared budget/capacity is provisionally reserved
  across the await and released on refusal/cancellation. Post follows spawn emission;
  only `continue` is valid and notification failure is observational.
- `querySpawnLog(store, parent, { childId?, role? })` strictly decodes physical parent
  JSONL records in append order. It neither expands fork ancestry nor consults live
  state, mutates logs or fabricates missing legacy provenance. Returns existing
  `subagent.spawn` events; optional additive `taskText` is the exact input while
  `task` remains the existing display label. This is a spawn-record query, not a
  completion-status API. Concurrent incomplete/corrupt JSONL remains an error.
- Gate-growth justification: the only new gate is the requested generic pre-spawn
  seam, with timeout/denial/reservation/extension-production fixtures. No CLI flag,
  shipping check, workflow field, issue policy or manual skill rule is added.

## Sequence and band acceptance

R19a → R19b → R19c → R19d → R19e → R19f. Dependencies are deliberately
sequential: generic mechanisms precede contribution points, which precede extracting
the pack, then extracting the train, retiring old bolt-ons, and finally replacing
manual gates with pack hooks. A later row does not start merely because its code
could be written in parallel; its prerequisite must merge first.

Band acceptance requires all six row acceptances, green exact-head and post-merge CI
for each serialized PR, compatibility shims only for the periods named above, and no
workflow-specific knowledge left in the harness surfaces identified for migration.
This definition PR satisfies none of those runtime acceptances.

### R19a provider-bound role slice

Agent-role frontmatter accepts optional `provider: <entry-name>` (1–128 characters,
`^[a-z][a-z0-9-]*$`), naming a configured provider entry, including the flat `default`
entry. This is a host-provider reference, never a model ID, endpoint or credential.
It takes precedence over the legacy `model-role` routing field. A bound entry must
appear in the host's `SubagentOptions.providerChoices.names`; otherwise spawning
refuses before lifecycle hooks, child configuration or startup. CLI wiring exposes
its entry catalogue for bound roles even with flat-only configuration. Existing
unbound roles retain `model-role` routing and unnamed children retain the configured
subagents default. As before, `agent` and caller `provider` cannot be supplied together.
Role tool/turn/delegation restrictions, budgets and permission mediation are unchanged.
Provider selection remains recorded in the existing child provider/context events;
role origin/hash provenance binds the manifest containing the provider reference.

This coherent slice does not implement skill includes/assets/flags. The final slice below
provides graph resolution, asset containment and flag semantics proof, including deterministic
ordering and invalid/cyclic rejection.
R19a is complete through #549, #559 and #562; both declared independent reviews of the final mechanism slice passed.
