# R10c — opt-in isolated parallel subagents

Status: implemented; one review's material findings addressed, delivery gates pending.

## Runtime contract

Trusted SDK callers select `subagentTool({ isolation: "worktree", ... })` and the
parent's `turnStrategy: parallel()`. Default/sequential legacy configurations are
unchanged. Every opted-in child receives a different checkout, including children
with unknown/exec tools; no name or read-only heuristic chooses writers. The exact
factory object has private runtime identity. A copied tool or model metadata cannot
recover the bridge. Opt-in with sequential scheduling still isolates, but does not
parallelize. This is not a CLI/config strategy loader or R15l workflow engine.

The normal final hook/schema/permission/audit pipeline runs first. A FIFO preparation
gate remains held through child configuration, budget reservation and checked worktree
creation; it releases only when the isolated checkout is ready. Isolated children may
overlap one another, but are barriers against ordinary parent tool calls. Existing
configured-hook/checkpointer/background exclusive fallback is preserved. Shared Git
allocation also uses a create-directory lock, with explicit contention refusal and
no stale-owner stealing. Preparation and synchronous `child.run()` failures release
live pool reservations; unknown spend remains conservatively reserved and failed
attempts consume the existing child-count cap. Spawn/end records remain paired.

No permission grants are remapped. A grant for a specific parent file or exact parent
cwd does not cover the different child file/cwd, even when delegable. An explicitly
broad ancestor path prefix may already contain the Git-metadata artifact directory;
its original lexical match is preserved, not silently narrowed or widened. Existing child views,
revocation, base-policy rules, fresh external-input consent and sandbox policy remain
independent. Explicit blanket authority remains broad. Model text/child summaries/
candidate manifests confer no authority.

## Sandbox and isolation limits

Worktree preparation explicitly refuses inside an enforcing **parent** sandbox: it
requires host Git metadata operations outside the one-cwd mount contract. This is
an ordinary refusal, not a sandbox escape request. A parent running without an OS
sandbox may supply an enforcing **child** sandbox. Its linked `.git` pointer may be
inaccessible there; child Git commands can fail. We neither expose writable common
Git metadata nor invent a second Git server or automatic outside-sandbox execution.

Distinct worktree cwd prevents ordinary relative file tools from sharing a checkout.
It is cooperative scheduling, not containment of broad exec, explicit absolute paths,
external writers or arbitrary trusted host JavaScript. Worktree siblings share Git
object metadata. A trusted child with ambient access can still mutate outside cwd;
permissions/OS sandboxing must supply that boundary. Captures detect observed races,
not all possible concurrent edits. Child/background operations are not forcibly
quiesced; aborted/non-done or reported-background children get no ready candidate.

## Baseline, retained artifacts and bounds

Only a Git worktree-root cwd is accepted. The runtime root is the canonical Git
common directory's `agentrig-isolated/`, containing unique `child-*/worktree/`
checkouts plus manifests and patches. It is structurally outside ordinary worktree
capture, without editing ignore rules, HEAD or the user's index. Session-store roots
are explicitly excluded from both parent captures. Exclusions canonicalize existing
ancestors while preserving the complete suffix of a not-yet-created store; neither
aliased stores nor lazy creation widen the exclusion to the repository. Unusual in-worktree common-Git
locations and symlinked artifact roots refuse.

The existing raw checkpoint state implementation captures tracked and nonignored
untracked files, including dirty bytes, with double-capture and HEAD/index identity
checks. Ignored untracked files and excluded runtime stores are outside coverage.
There is no assumption that `HEAD` or a clean status represents the working state.
The baseline tree is placed in a detached synthetic commit and materialized as raw
blobs, without checkout smudge/clean filters, CRLF conversion or hook execution.
The new checkout is checked against that raw tree. The parent baseline is rechecked
after preparation. No branch or parent checkout is rewritten.

Bounds: 50,000 captured paths; 4,096 characters and 128 components/path; regular files up to 16 MiB;
128 MiB aggregate captured bytes; 8 MiB binary diff; no submodules, symlinks, special
files, unsupported portable path forms or case/normalization aliases. Capture Git
commands have existing bounded output/time limits and cancellation. Materialization
uses an explicitly bounded byte buffer and awaited file writes.

At most eight retained allocation directories per repository are admitted. Before
allocation, a bounded no-symlink inventory (100,000 entries) requires retained bytes
to leave a 136 MiB reserve inside a 512 MiB capacity. This is an admission/capture
bound, **not** a filesystem quota: trusted running children can exceed it, Git object
storage is not included, and external writers are outside the cooperative contract.
Subsequent allocation refuses when capacity/inventory cannot be established. Existing
child/session/depth/token pools remain additional bounds.

Everything is retained, including partial preparation and failed/aborted captures.
The result reports the exact retained location where available. No force cleanup,
branch deletion, automatic worktree removal or abandoned destructive I/O is used.
Operators must stop writers and explicitly inspect/remove the named retained worktree
and artifacts before reclaiming capacity; a crashed allocation lock needs the same
quiescent manual recovery. There is no age-based cleanup.

## Parent diff handoff

A done child with no reported background work is captured into a raw result tree.
`candidate.patch` is a bounded binary diff from the exact baseline; `candidate.json`
records child identity, cwd, baseline state, result tree, changed paths and patch path.
The parent must still match the captured baseline before `ready: true` is recorded.
An observed parent edit instead retains a stale candidate and returns a tool error;
unsupported/oversized/aborted captures retain the checkout without a ready candidate.

Readiness is a point-in-time observation, not atomic compare-and-apply or standing
permission. The parent inspects the diff and applies it through normal authorized
tools in a later turn (for example explicit `git apply --check` then `git apply`).
Those commands are not crash-atomic ownership enforcement. Intervening edits require
rechecking; overlapping child diffs can conflict and are never automatically three-way
merged. Child file changes are not forwarded as parent `file.changed` progress; only
actual parent integration can supply normal parent mutation evidence.

## Verification record

Local fake providers and real owned temporary Git repositories only; no live model
calls or network spend. Actual runtime controls cover simultaneous writer entry,
different cwd, dirty/untracked preservation, reversed completion versus model result
order, contiguous events, parent deny then explicit apply, conflicting patch rejection,
delegable path/cwd grant refusal, copied factory identity, parent sandbox refusal,
stale/aborted retention, unsupported/oversized baseline, smudge-filter avoidance and
preparation/synchronous-run pool cleanup. Supervisor tests pin call-relative loop and
stall behavior with both completion orders, including withdrawal of failed calls'
variation credit. These advisory detectors do not mistake retained child candidates
for parent file progress.

Named negative controls, each restored: forcing candidate readiness true fails the
actual stale-parent test (`ok: true` instead of refused); making isolated cohorts
exclusive fails the two-writer simultaneous-entry barrier at its explicit 20s bound
(the finally releases/joins both children); removing early-failure live-pool decrement
fails all three non-Git/retention/synchronous-run controls (`live: 1` rather than zero).
Initial build/typecheck and full suite pass 2,644 plus two existing skips / 151 files
(four workers, 39 seconds).
