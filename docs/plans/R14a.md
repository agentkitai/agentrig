# R14a — observable acceptance declarations

The committed row asks the model to emit `update_plan` with an `accept` field per item on the
first turn; it does not mandate a new execution or completion gate. Canonical PlanItem and tool
input therefore share an optional, nonblank, at-most-1024-character free-text check. Legacy items
remain valid and visibly undeclared/unverified. Declaration text is never executed or treated as
authority; an item marked done still has an unverified check.

When `update_plan` is available, the first actual model request of each run (including resume)
adds a small runtime platform instruction asking for the complete plan and observable checks.
Existing custom prompt/hook text is preserved. The instruction is part of the context manifest
and is appended after pre_model hooks: those hooks do not observe or adjust this final platform block.
It is not a user steer or fresh consent, and never clears R13c's sticky restriction. Later requests do
not repeat it. No extra provider request, forced tool call, or mandatory acceptance validator is
introduced; a model may ignore the request and answer normally.

The field survives validated tool dispatch, plan.updated, immutable session storage, resumed
message history, the supervisor's ordinary plan fold, and tool/CLI/TUI plan displays. Displays
distinguish declared checks from missing legacy declarations and label both unverified. This row
does not match evidence, execute checks, infer outcome, change the grader, or add --evidence.
