# H5c1 — guarded dream snapshots and apply

Starts from updated main 3eee3ea after PR #124 and green main CI 33961430044.

The current copy/apply code neither snapshots under the memory mutation lock nor checks for
intervening edits. It accepts pre-existing copy destinations, removes a deterministic staging
path without establishing ownership, and compares roots only lexically. Existing rollback tests
do not actually inject the failing renames they name. Close these gaps before wider dream work.

Plan:

- Copy only into a fresh, owned directory; refuse canonical source/destination overlap. Record
  canonical source root, root identity and content fingerprint in a versioned sibling manifest.
  Snapshot under the same lock as store writers; no model call holds that lock.
- Require the manifest to apply. Lock source and output in canonical order, verify source identity
  and fingerprint, stage into a unique owned sibling, preserve the original backup, then swap.
  Existing backup paths are never overwritten; stamps cannot contain path components.
- Preserve the live scheduling stamp separately from content. `.last-dream` is maintenance
  metadata, not part of the content fingerprint; stamp writes must also use the shared lock.
- Refuse stale or unregistered output. Keep normal review artifacts inspectable across processes.
  Dispose only a directory whose saved identity/ownership still matches, while respecting its
  mutation lock. Never remove an unrelated deterministic staging path or a replacement owner.
- Exercise actual two-process writer/apply serialization, alias/overlap/stale/ownership cases,
  real second-rename and restore failures, and backup/target preservation.

This is cooperative-writer coordination, not protection against a hostile host changing paths
between filesystem calls. The two directory renames are not a reader-atomic transaction; locked
writers cannot enter the gap, but unlocked readers can briefly see a missing root. A failed restore
must name the preserved backup and staging paths for stopped-writer recovery.

H5c2 owns full scan/provider bounds, linked dream cancellation/accounting, and explicit crash-left
workspace/sidecar recovery. H5c3 owns legacy lossless regeneration and session-scoped ledger lookup.
H5c4 owns the remaining historical staged-abort investigation. No claim that these are done here.
